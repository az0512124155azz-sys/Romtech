# חיבור Supabase ב־RomTech — מדריך למוכר

## מה כלול

בניהול נוסף מסך **חבר Supabase**. לאחר הגדרת סביבת האתר, הקונה מתחבר לחשבון שלו, בוחר פרויקט או יוצר חדש, מפעיל הכנה אוטומטית ובדיקה, ומפעיל את החיבור. אחר כך אפשר להעביר את הנתונים מהמכשיר שבו נוהלה החנות.

האתר משתמש בשרת Node וב־Supabase Database/Storage. פרטי החיבור נשמרים ב־Redis משותף; מכשיר חדש רואה את אותו פרויקט. הקונה אינו צריך להדביק מפתחות או SQL.

## הכנה חד־פעמית לכל התקנה

1. חבר את המאגר ל־Vercel. בחר תיקיית שורש ו־Framework: Other. `vercel.json` מגדיר `npm run build`, פלט `dist` ופונקציית שרת. ודא שאין הגדרות Build/Output ישנות שגוברות עליו.
2. צור Redis תואם ל־Upstash REST, למשל באמצעות Vercel Marketplace. אפשר לשתף Redis בין התקנות עם `ROMTECH_STORE_PREFIX` נפרד לכל אחת.
3. צור סיסמת בעל אתר באורך 12 תווים לפחות עם `npm run owner-password`. ההקלדה מוסתרת והכלי מחזיר hash להצבה בשרת. מסור לקונה את הסיסמה בדרך פרטית; הוא יכול להחליף אותה בניהול. הקוד המקומי הישן אינו נותן הרשאות לשרת.
4. צור מפתח הצפנה של 32 בתים אקראיים ב־Base64, למשל `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"`. שמור אותו מאובטח וקבוע לאורך פריסות; שינויו ינתק גישה למידע המוצפן ב־Redis.
5. ב־Supabase, פתח [Organization → OAuth Apps](https://supabase.com/dashboard/org/_/apps) ורשום אפליקציית RomTech. הרשאות: `organizations:read`, `projects:read`, `projects:write`, `database:write`, `secrets:read`, `secrets:write`. הקונה מאשר בהמשך גישה לחשבון שלו.
6. רשום Redirect URI מדויק של האתר, לדוגמה:

   ```text
   https://romtech-alpha.vercel.app/api/romtech?action=oauth-callback
   ```

   הכתובת צריכה להתאים בדיוק ל־`ROMTECH_ORIGIN` ולנתיב הזה. לעותק בדומיין אחר, הגדר callback של אותו עותק ברישום ה־OAuth שלו.
7. הגדר משתני **שרת בלבד** ב־Vercel. אין להכניס ערכים אמיתיים למאגר או ל־HTML:

   | משתנה | ערך |
   |---|---|
   | `ROMTECH_ORIGIN` | מקור HTTPS הקבוע של האתר, ללא נתיב |
   | `ROMTECH_STORE_PREFIX` | מזהה ייחודי להתקנה ולסביבה, למשל `romtech-production` |
   | `UPSTASH_REDIS_REST_URL` | כתובת REST של Redis; אופציונלי אם Vercel יצר `KV_REST_API_URL` |
   | `UPSTASH_REDIS_REST_TOKEN` | סוד הגישה ל־Redis; אופציונלי אם Vercel יצר `KV_REST_API_TOKEN` |
   | `ROMTECH_ENCRYPTION_KEY` | מפתח ההצפנה |
   | `ROMTECH_OWNER_PASSWORD_HASH` | תוצאת הכלי ליצירת סיסמה |
   | `SUPABASE_OAUTH_CLIENT_ID` | מזהה אפליקציית OAuth |
   | `SUPABASE_OAUTH_CLIENT_SECRET` | סוד אפליקציית OAuth |

8. פרוס מחדש. השתמש בסביבה וב־Redis prefix נפרדים עבור Preview/בדיקות. התחבר ב־`/admin/` וודא שכפתור החיבור פעיל.

`.env.example` מציג שמות בלבד. מקומית: `npm ci`, `npm run build`, `npm run dev`. `.env.local` אינו נכנס למאגר. האתר המקומי ב־`http://127.0.0.1:4173`; OAuth אמיתי דורש callback מקומי רשום.

המאגר כולל גם מסלול Netlify הקיים: `netlify.toml` ופונקציית שרת ב־`netlify/functions/romtech.mjs`. אם משתמשים בו, הגדר את אותם משתנים בסביבת Functions של Netlify ואת `ROMTECH_ORIGIN`/callback לפי הדומיין שלו. הפריסה מפרסמת רק `dist` ומצרפת את הפונקציה בנפרד. אין להעלות את תיקיית המאגר כולה כקבצים ציבוריים.

## זרימת הקונה

1. כניסה לניהול ולחיצה על **חבר Supabase**, התחברות ואישור בחלון Supabase.
2. בחירת פרויקט פעיל או יצירת פרויקט בארגון שלו לאחר אישור התוכנית והמכסה. ההקמה עשויה להימשך דקות; רענן עד שהפרויקט פעיל. לאחר תגובה לא ודאית ליצירה, בדוק את הרשימה לפני שליחה חדשה.
3. **הכן את הפרויקט**: טבלאות והרשאות נוצרות בטרנזקציה, לצד מפתחות ואחסון. נבדקות גישה לקטלוג ופרטיות הזמנות. רצוי פרויקט ייעודי; ההכנה מוסיפה משאבי `romtech_` לפרויקט שנבחר.
4. **הפעל חיבור לפרויקט שנבדק**. עד לשלב זה החיבור הקודם נשאר פעיל.
5. במכשיר המקורי, **העבר נתונים מקומיים**: בדיקת הספירות ואישור. תמונות מועלות ל־Storage ורשומות חסרות מתווספות. מזהה שקיים אינו מוחלף. ניתן להריץ שוב לאחר תקלה; המקור נשמר כגיבוי. סיסמאות והעדפות גלישה אינן מועברות.
6. בדיקה במכשיר שני. בניהול אפשר לבדוק תקינות, להחליף פרויקט או לנתק. ניתוק משבית קטלוג וקבלת הזמנות עד לחיבור מחדש; הוא אינו מוחק נתונים בפרויקט.

## נתונים ואבטחה

הטבלאות בסכמת `public`, עם קידומת ייעודית ו־RLS:

| טבלה | גישה ציבורית |
|---|---|
| `romtech_products` | מוצרים מפורסמים בלבד; עמודת העלות מוגנת בהרשאות עמודה |
| `romtech_orders` | אין קריאה או כתיבה ישירה לציבור |
| `romtech_reviews` | ביקורות מאושרות בלבד |
| `romtech_settings` | פרטי האתר הציבוריים |
| `romtech_content` | תוכן העמודים הציבורי |
| `romtech_schema` | שרת בלבד, לגרסת ההתקנה |

לקוחות נגזרים מהזמנות. מחיר הזמנה, שם מוצר וסטטוס ראשוני נקבעים בשרת. הזמנה דורשת אישור שימוש בפרטים. ביקורות תקינות מתפרסמות מיד לפי התנהגות העמוד המקורי, וניתנות למחיקה בניהול.

Bucket `romtech-images` ציבורי לצפייה, מוגבל ל־PNG/JPEG/WebP ול־2MB לקובץ. רק השרת לאחר אימות בעל האתר מעלה ומחליף תמונות. שמות מבוססי hash מאפשרים העברה חוזרת. קבצים שאינם בשימוש אינם נמחקים אוטומטית.

ניהול מאומת בשרת עם סיסמת בעל אתר, HttpOnly/SameSite cookie, בדיקת מקור והגבלת ניסיונות. OAuth של חשבון Supabase משמש להרשאת הקמה. משתמש Supabase Auth רגיל אינו מקבל הרשאות ניהול בחנות.

הדפדפן מקבל URL ומפתח `sb_publishable_` בלבד. השרת משתמש במפתח `sb_secret_` ייעודי, שמוצפן ב־AES-256-GCM ב־Redis ואינו מוחזר לדפדפן. המפתח נותן גישה רחבה לפרויקט; הגן על משתני השרת ובחר פרויקט ייעודי. הרשאת Management OAuth מוצפנת ונשמרת רק במהלך ההקמה, לכל היותר שעה; refresh tokens אינם נשמרים. אין `service_role` או secret key בקוד הלקוח.

SQL לעדכונים משתמש ב־`SECURITY INVOKER`, ורק תפקיד השרת יכול להריצו. עריכות בודקות revision ומחזירות שגיאה בשינוי מקביל. כשל ענן אינו הופך לכתיבה מקומית שקטה. נתונים ציבוריים מתרעננים בחזרה לעמוד ובכל 30 שניות; בניהול כפתורי הרענון טוענים מהשרת.

## תקלות נפוצות

- **כפתור לא פעיל:** השלם משתני שרת/OAuth. ללא שרת מוגדר זו הדגמה מקומית עם הודעה; הזמנות וביקורות אינן מוצגות כאילו נשלחו.
- **OAuth פג:** לחץ שוב על חבר Supabase. חיבור שכבר הופעל ממשיך עם מפתח השרת.
- **מכסת פרויקטים:** בחר קיים או בדוק תוכנית חשבון. RomTech אינו משהה או מוחק פרויקטים אחרים.
- **פרויקט בהקמה:** המתן ורענן.
- **Bucket קיים עם הגדרות שונות:** ההכנה נעצרת; בדוק את `romtech-images`.
- **שינוי ממכשיר אחר:** רענן ובצע מחדש את העריכה.
- **מפתח שרת בוטל:** התחבר והפעל הכנה מחדש.
- **שחזור סיסמה:** שינוי בניהול מבטל sessions אחרים. בעל התשתית יכול להסיר ב־Redis את `<ROMTECH_STORE_PREFIX>:owner` ולהציב hash חדש בשרת. קוד מקומי אינו עוקף את האימות.
- **החלפת דומיין:** עדכן `ROMTECH_ORIGIN`, רשום callback מדויק ופרוס מחדש.

## בדיקות ומה נדרש בסביבה חיה

`npm test` בודק SQL מול PostgreSQL באמצעות PGlite, כולל RLS, grants, פרטיות, התנגשויות וטרנזקציות, ואת שרת החיבור מול ספק מדומה. `npm run test:browser` בודק דפדפן מול שרת RomTech עם ספק Supabase מדומה: חיבור, הכנה, הפעלה, תמונה, שני דפדפנים, הזמנה וביקורת, כשל שמירה, יצירה, החלפה וניתוק.

אפליקציית OAuth עדיין לא נרשמה ולכן התחברות אמיתית לחשבון Supabase לא נבדקה. אחרי ההגדרה יש לעבור את הזרימה בפרויקט בדיקה ייעודי, להריץ **בדוק תקינות** ולשלוח הזמנה וביקורת ממכשיר שני. בדיקות עם ספק מדומה אינן מוכיחות שההרשאות ותשתית האירוח כבר הוגדרו.
